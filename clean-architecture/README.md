### '매핑하지 않기' 전략에서 '양방향 매핑' 전략으로 변경 후
여기서는 순수 자바 코드로만 작성하다보니 실제 프로젝트 환경이랑 조금 다를 수 있다.

- 기존에 했던 프로젝트들에서 보통 웹쪽은 별도의 입출력 DTO 를 두고 했었다.
  - API 스펙이 바뀌는 빈도가 잦기도 하고, 응답으로 도메인 엔티티를 그대로 노출할 수 없기 때문
- 반면 영속성 계층을 위한 별도의 모델을 둔 적은 없었다.
  - 도메인 모델에 JPA 어노테이션을 달아서 영속성 모델로도 사용함.
- 영속성 계층의 모델을 따로 두니, 도메인 객체는 테이블 설계로 부터 영향을 안 받게 된다.
- 예를 들어, auditing 용도의 변경일자 필드 `AccountEntity.updateAt` 를 영속성 모델에 추가했지만, 도메인 객체에는 필요없는 필드이다.

결론 : 웹 계층과 영속성 계층에 별도의 모델을 두니, 확실히 도메인 객체 자체의 설계가 깔끔해진다.
