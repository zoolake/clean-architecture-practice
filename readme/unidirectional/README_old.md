### '완전 매핑' 전략에서 '단방향 매핑' 전략으로 변경 후
여기서는 순수 자바 코드로만 작성하다보니 실제 프로젝트 환경이랑 조금 다를 수 있다.

- 웹 모델, 도메인 모델, 영속성 모델 모두 동일한 인터페이스를 구현한다.
- 다형성을 활용하여 계층 간 모델을 넘길 때 별도의 매핑을 안해줘도 넘길 수 있다.

### 웹 ↔︎ 어플리케이션
코드 작성과정에서 아래와 같은 문제점이 있었다.
- 모든 모델들이 같은 인터페이스를 구현하고 있다. -> 계층 간 데이터 전달 과정은 다형성을 통해 편리할 것으로 예상했음
- 그런데 웹 계층에서 받은 정보를 어플리케이션 계층으로 넘길때 필요한 정보들을 넘기기 오히려 번거롭다.
  - 예를 들어 다음과 같이 웹 모델과 도메인 모델이 구성되어 있다고 가정하자.
    - 웹 모델 : `SendMoneyRequest:{sourceAccountId, targetAccountId, amount}`
    - 도메인 모델 : `Account:{accountId, balance}`
    - 인터페이스 : `AccountState(I):{getAccountId(), getBalance()}`
  - 웹 계층에서 `SendMoneyRequest` 를 어플리케이션 계층으로 그대로 넘길 순 있으나, 다음과 같은 부분이 걸린다.
    - 웹 모델의 필드인 `amount` 는 `AccountState(I)` 에서는 다루지 않는데 어떻게 해야하나?
    - 인터페이스에는 `getAccountId()` 가 있는데 웹 모델의 필드에는 `targetAccountId` 와 `sourceAccountId` 가 있다.
    - 즉, 같은 인터페이스를 구현하기 때문에 웹 계층의 요구사항이 인터페이스에 영향을 끼치고, 같은 인터페이스를 구현하는 도메인 모델에도 영향을 끼치게 되는 것 같다.

결국 일단 단방향 매핑 전략으로 구현하기 위해 웹 계층에서 외부로 부터 입력을 받는 `SendMoneyRequest` 는 `AccountState(I)` 를 구현하지 않게 하고,
웹 어댑터에서 별도로 정적 내부 클래스로 `AccountState(I)` 를 구현하는 구현체 `AccountStateImpl` 를 선언했다.
그리고 웹 계층에서 어플리케이션 계층으로 모델을 넘기기 위해 `SendMoneyRequest` 를 `AccountStateImpl` 로 매핑하고 `AccountStateImpl` 을 넘기는 방식으로 구현했다.

### 어플리케이션 ︎︎↔︎ 영속성
구현 과정에서 단방향 매핑 전략은 웹 ↔︎ 어플리케이션 보다는 어플리케이션 ↔︎ 영속성 관계에서만 적용하는게 타당하다는 생각이 들었으며, 이유는 아래와 같다.
- 웹 ↔︎ 어플리케이션 보다는 상대적으로 도메인 모델과 영속성 모델이 유사할 확률이 높다. (작은 규모일수록)
  - 당장 내가 했던 QR 연락처 프로젝트만 봐도 JPA 엔티티(영속성 모델)을 도메인 모델로 그냥 사용한다.
- 어플리케이션 ↔︎ 영속성 상황에서 사용하면 JPA 를 사용하는 환경에서는 도메인 모델과 영속성 모델을 분리할 수 있게 되며, 영속화 과정에서 도메인 모델로 부터 필요한 정보는 인터페이스를 통해 다 얻어낼 수 있다.


책에는 다음과 같은 내용이 있다.
- 단방향 매핑 전략은 계층 간의 모델이 비슷할 때 가장 효과적이다.
  - 즉, 계층 간 모델이 비슷할 때는 어느정도 각 계층 별 모델의 독립성도 보장하면서 계층 간 데이터 이동에도 다형성을 통해 편리함을 추구하려는 목적인 전략인 것 같다.
  - 그런데 송금 기능을 기반으로 진행하는 현재 상황에서는 조금의 차이가 생기는 순간부터 해당 전략의 실효성이 사라지는 듯 하다.
- 매핑 책임은 아래와 같다.
  - A → B : B 에서 매핑 담당
  - A ← B : A 에서 매핑 담당

내 생각을 정리하면 아래와 같다.
- 웹 ↔︎ 어플리케이션 간의 모델 전송 과정에서 사용하기에는 다소 무리가 있다.
  - 웹 모델과 어플리케이션 모델 간의 괴리가 크기 때문
- 반면, 어플리케이션 ↔︎ 영속성 모델 전송 과정에서는 적합하다고 생각한다.
  - 물론 웹 모델과 어플리케이션 모델 간 괴리가 있듯이, 어플리케이션 모델과 영속성 모델 간 괴리는 존재한다.
  - 다만 상대적으로 적을 확률이 높기 때문에 작은 규모의 프로젝트에서는 적합할 것 같다.
