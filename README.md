# '양방향 매핑' 전략에서 '완전 매핑' 전략으로 변경 후 리뷰

> 현재 순수 자바 코드로만 작성하여 테스트 중이므로 실제 프레임워크 기반 프로젝트 환경과는 다소 차이가 있을 수 있다.

## 📊 매핑 전략 구조 비교

- **양방향 매핑 전략**: 웹 모델, 도메인 모델, 영속성 모델로 계층이 분리되어 구성된다.
- **완전 매핑 전략**: 인커밍/아웃고잉 포트 인터페이스에서 사용하는 별도의 **커맨드(Command) 모델**이 추가된다.

## 🤔 완전 매핑 전략 도입에 대한 실효성 고민

현재 유스케이스 규모에서는 포트 인터페이스에 별도의 커맨드 모델을 추가하는 것에 대한 실효성이 크게 체감되지 않는다. 매핑 단계가 늘어나 구조가 복잡해지기 때문이다.

- **양방향 매핑 흐름**: `웹 모델 → 도메인 모델 → 영속성 모델`
- **완전 매핑 흐름**: `웹 모델 → 커맨드 모델 → 도메인 모델` / `도메인 모델 → (커맨드 모델) → 영속성 모델`

어플리케이션 계층과 영속성 계층 사이에는 **매핑 오버헤드**가 크므로 완전 매핑 전략을 사용하는 것이 권장되지 않는다고 한다. 향후 '계좌 조회', '계좌 생성' 등 유스케이스가 다양해졌을 때 이 구조의 장단점을 다시 평가해 보아야 할 듯하다.

## ⚠️ 인커밍 포트 전용 객체(Command) 부재 시 발생할 수 있는 문제점

포트가 도메인 모델을 직접 사용하게 되면 다음과 같은 설계적 결함이 발생할 수 있다.

1. **도메인 모델의 외부 입력 형태 변질 및 검증 로직 분산**
   웹 어댑터가 입력값을 도메인 모델로 매핑할 때, 도메인 모델이 외부 입력을 받기 편한 형태로 오염될 수 있다. `User` 도메인 모델을 사용할 때 웹에서 `passwordConfirm`을 입력받는다면, 도메인 모델에 불필요한 필드를 추가하거나 웹 어댑터 쪽에 검증 로직이 파편화되는 문제가 발생한다.

2. **불완전한 도메인 모델 생성 위험 (부분 업데이트 시)**
   연락처(`phoneNumber`)만 업데이트하는 요청이 들어올 경우, 웹 어댑터에서 도메인 모델로 매핑 시 변경하지 않는 값(`id`, `password`)은 `null`이나 빈 값으로 처리해야 한다. 이는 도메인 모델에 옵셔널 생성자를 강제하게 만들며, 결과적으로 불완전한 상태를 가진 도메인 객체가 생성될 위험성을 내포한다.

## 💡 결론: 인커밍 포트에서 별도의 Command 객체를 두는 이유

- 도메인 객체가 감당하기에 **모호하거나 불필요한 입력값**(예: 비밀번호 확인)을 전용 객체를 통해 안전하게 받아낸다.
- 부분 업데이트처럼 특정 필드만 필요한 경우, 도메인 객체를 불완전하게 만드는 대신 **명확한 의도를 가진 커맨드 객체**를 통해 값을 전달받는다.
