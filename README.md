# '완전 매핑' 전략에서 '단방향 매핑' 전략으로 변경 후 리뷰

> 현재 순수 자바 코드로만 작성하여 테스트 중이므로 실제 프레임워크 기반 프로젝트 환경과는 다소 차이가 있을 수 있다.

## 📊 단방향 매핑 전략 특징

- 웹 모델, 도메인 모델, 영속성 모델 모두 **동일한 인터페이스**를 구현한다.
- **다형성**을 활용하여 계층 간 모델을 넘길 때 별도의 매핑 과정 없이 전달할 수 있다.

## ⚠️ 웹 ↔︎ 어플리케이션 계층 간 매핑의 한계

코드 작성 과정에서 모든 모델이 같은 인터페이스를 구현하는 구조가 오히려 번거로움을 유발하는 문제점이 있었다.

- 웹 계층에서 받은 정보를 어플리케이션 계층으로 넘길 때 필요한 정보를 전달하기 까다롭다.
   - **웹 모델**: `SendMoneyRequest:{sourceAccountId, targetAccountId, amount}`
   - **도메인 모델**: `Account:{accountId, balance}`
   - **인터페이스**: `AccountState(I):{getAccountId(), getBalance()}`
- **발생하는 문제점**:
   - 웹 모델의 `amount` 필드는 `AccountState(I)`에서 다루지 않으므로 처리 방식이 모호해진다.
   - 인터페이스는 `getAccountId()`를 요구하지만, 웹 모델은 `targetAccountId`와 `sourceAccountId`를 가진다.
   - 즉, 웹 계층의 요구사항이 인터페이스에 영향을 미치고, 동일한 인터페이스를 구현하는 도메인 모델까지 영향을 받게 되는 구조적 결함이 발생한다.

### 💡 임시 해결책
웹 계층 외부 입력을 받는 `SendMoneyRequest`는 `AccountState(I)`를 구현하지 않도록 하고, 웹 어댑터 내부에 별도의 정적 내부 클래스(`AccountStateImpl`)를 선언하여 인터페이스를 구현하도록 했다.
결과적으로 모델 전달을 위해 `SendMoneyRequest`를 `AccountStateImpl`로 매핑하여 넘기는 방식으로 우회하여 구현했다.
→ _**근데 이렇게 되면 웹 ↔︎ 어플리케이션 은 양방향 매핑이 된다.**_

## 🤔 어플리케이션 ↔︎ 영속성 계층 적용의 타당성

단방향 매핑 전략은 웹 ↔︎ 어플리케이션 구간보다 **어플리케이션 ↔︎ 영속성 관계**에 적용하는 것이 더 타당하다고 판단된다.

- **모델 간의 유사성**: 웹 모델에 비해 도메인 모델과 영속성 모델이 유사할 확률이 훨씬 높다 (특히 소규모 프로젝트의 경우).
   - 예시: QR 연락처 프로젝트에서도 JPA 엔티티(영속성 모델)를 도메인 모델로 그대로 사용함.
- **영속화 과정의 이점**: JPA 사용 환경에서 도메인 모델과 영속성 모델을 분리하면서도, 영속화에 필요한 정보는 인터페이스를 통해 모두 얻어낼 수 있다.

## 📚 책에서 언급된 내용

- 단방향 매핑 전략은 **계층 간의 모델이 비슷할 때 가장 효과적**이다.
   - 각 계층 모델의 독립성을 어느 정도 보장하면서 데이터 이동의 편리함을 추구하는 전략.
   - 하지만 송금 기능과 같이 모델 간에 조금이라도 차이가 생기는 순간 해당 전략의 실효성이 크게 떨어진다. (내 생각)
- **매핑 책임**:
   - `웹 → 어플리케이션`: **어플리케이션**에서 매핑 담당
   - `웹 ← 어플리케이션`: **웹**에서 매핑 담당
   - 양방향 매핑 전략에서는 `웹 → 어플리케이션` 와 `웹 ← 어플리케이션` 둘 다 웹에서 매핑을 담당한다.

## 💡 내가 생각한 결론

- **웹 ↔︎ 어플리케이션 전송**: 적용하기 다소 무리가 있다.
   - 웹 모델과 어플리케이션 모델 간의 형태적 괴리가 크기 때문이다.
- **어플리케이션 ↔︎ 영속성 전송**: 적용하기 적합하다.
   - 어플리케이션 모델과 영속성 모델 간에도 괴리는 존재하지만, 상대적으로 유사할 확률이 높아 작은 규모의 프로젝트에서는 유효한 전략이다.
   - 만약 인터페이스가 계속 모델에 영향받아서 수정되어야 하는 상황이 지속된다면 양방향 매핑으로 전환하는게 더 좋을 것 같다.
      - 단방향의 장점은 다형성을 통한 매핑 과정 생략인데 이를 포기하고 변경에 강한 구조가 양방향 매핑이라고 생각하기 때문
