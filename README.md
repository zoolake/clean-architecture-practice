### '양방향 매핑' 전략에서 '완전 매핑' 전략으로 변경 후
여기서는 순수 자바 코드로만 작성하다보니 실제 프로젝트 환경이랑 조금 다를 수 있다.

- 양방향 매핑 전략에서는 웹 모델, 도메인 모델, 영속성 모델로 구성되어 있었다.
- 완전 매핑 전략에서는 인커밍/아웃고잉 포트 인퍼테이스에서 사용하는 별도의 커맨드 모델을 추가했다.
- 근데 일단 현재 방식? 규모? 에서 포트 인터페이스에 별도의 모델을 추가하니 실효성을 못느끼겠다.
  - 양방향 매핑 전략에서는 웹 모델 → 도메인 모델 / 도메인 모델 → 영속성 모델로 가던 과정에서
  - 완전 매핑 전략에서는 웹 모델 → 커맨드 모델 → 도메인 모델 / 도메인 모델 → 커맨드 모델 → 영속성 모델 로 단계가 늘었다.
    - 어플리케이션 계층과 영속성 계층 사이에는 매핑 오버헤드로 인해 완전 매핑 전략을 사용하지 않는게 좋다고 한다.
  - 한번 다른 기능들, 예를 들어 계좌 조회/계좌 생성, 을 추가했을 때 위와 같은 구조가 어떨지를 봐야 할 듯.
    - 유스케이스가 현재는 하나 밖에 없으니 커맨드 모델을 추가해도 별 의미가 없음.
    - 유스케이스들이 더 많아졌을 때의 상황도 한번 봐야 할 듯.
    

인커밍 포트에서의 별도 객체를 두는 부분에 대한 실효성에 의문을 갖고 있었는데, 별도 객체를 두지 않게되면 다음과 같은 문제가 있을 수 있다.
- 포트가 도메인 모델을 사용하게 되면, 웹 어댑터가 입력값을 도메인 모델로 매핑해야 하는데 이는 곧 도메인 모델이 외부 입력을 받기 좋은 형태로 변할 수 있는 여지를 주게 된다.
  - 다음과 같은 상황을 가정해보자.
    - 포트가 User 라는 도메인 모델을 사용한다. `User:{id, password, phoneNumber}` 
    - 웹 어댑터에서 password와 passwordConfirm 을 입력받는다.
    - 포트가 도메인 모델을 사용하는 경우, passwordConfirm 에 대한 유효성 검증을 웹 어댑터에서 처리하거나 도메인 모델에 passwordConfirm 을 받는 필드를 추가해야 한다.
    - 즉, 검증 로직이 흩어지거나 위에서 언급한 도메인 모델이 외부 입력을 받기 위한 형태로 변형이 된다라는 문제가 생기게 된다.
- 상태 업데이트하거나 옵셔널한 필드가 섞여있는 경우에 문제가 될 수 있다.
  - 예를 들어, 특정 필드 하나만 변경하려는 요청이 들어왔을 때, 웹 어댑터에서 입력값을 도메인 모델로 매핑하는 과정에서 변경하려는 필드를 제외한 나머지 값들은 null 이나 빈값으로 두게 된다.
    - User 의 연락처 정보만 업데이트 하려고 하기 때문에 웹 어댑터에서는 다음과 같이 입력을 받는다. `{phoneNumber:010123456789}`
    - 기존 양방향 매핑 전략에서는 포트에서 도메인 모델을 사용하기 때문에 User 의 다른 정보 `{id,password}` 는 빈값이 들어간다.
    - 이렇게 되면 도메인 모델 클래스에 옵셔널하게 값을 받는 생성자가 필요할 수 있게 된다. → 불완전한 도메인 모델을 생성할 수 있는 여지가 생김


인커밍 포트에서 별도의 객체(Command) 를 두는 이유를 다시 정리하면
1. 도메인 객체가 받기에는 모호한 값들을 인커밍 포트 전용 객체를 통해서 받아낸다.
2. 부분 업데이트를 위한 값들을 인커밍 포트 전용 객체를 통해서 받아낸다.
